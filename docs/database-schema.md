# Kimbo database contract

Nine PostgreSQL tables implement the agreed schema. Prisma models use camelCase; database columns and tables use snake_case. No monthly goals, per-day schedules, standalone attachment/job tables, or provider secrets are stored.

| Table | Responsibility |
| --- | --- |
| users | Stable guest/member ownership, stable bearer identity, separate email/password credential hash, timezone, onboarding completion |
| user_health_profiles | Required onboarding facts and immutable local wake/sleep times |
| user_preferences | Preferred chat model, one row per user |
| entities | Owned dated health events, category, media JSON, input revision, soft deletion |
| entity_tag_details | User content, confirmed facts, and one current retryable AI workflow |
| health_records | Append-only measured/extracted/calculated observations and corrections |
| ai_models | Provider model identifiers, capabilities, availability, optional server credential reference |
| chat_threads | Owned conversations and model selection for subsequent requests |
| chat_messages | Ordered, idempotent messages with status, actual model and source metadata |

## Identity and onboarding

Guest registration updates the existing user rather than copying its data. Email is nullable and unique; normalize it before persistence. `auth_provider_id` is the stable bearer value: new guest/member accounts receive random UUIDs. Guest conversion preserves this value and the user's ID, onboarding state and all ownership. `password_hash` separately stores a salted scrypt hash of the normalized email and exact password encoded as a JSON array. It is never returned to clients. Existing member credential hashes are backfilled into the new column while their previous bearer values remain unchanged for compatibility.

Member creation requires email and password; sign-in verifies `password_hash` and returns the existing `auth_provider_id` as `token`. Guests have null name, email and password hash, but receive a UUID token. Passing that UUID as `authProviderId` to account creation atomically updates only the matching guest, subject to unique normalized email. No email verification or external identity provider is used. Protected product requests must validate the bearer value; expiry and revocation remain separate concerns.

Complete onboarding in one transaction: create the health profile, preferences and initial weight observation, then set users.onboarding_completed_at. Gate product operations on that timestamp in the backend. Onboarding drafts remain local. Age is stored with its recording date; no birth date is invented. Height is centimeters and weight kilograms. Initial profile weight is a snapshot; current weight comes from the latest applicable non-void weight observation.

Wake/sleep are PostgreSQL time values interpreted in users.timezone. Sleep earlier than wake means the next day. A SQL trigger rejects subsequent changes. These are configured boundaries, not observed sleep measurements. Timezones must be valid IANA names validated by the service.

## Entries and JSON contracts

Create entity details and its linked entity in a transaction. The unique required details FK gives each entity its own content record; unlinked details should not be created independently. Keep user ownership immutable and obtain it from authentication. Soft-delete entities; do not physically remove observations referenced by the append-only log.

entity_attachments is an array such as:

```json
[{"id":"attachment-uuid","type":"image","storageKey":"entries/id/photo.jpg","mimeType":"image/jpeg","fileSizeBytes":180000,"widthPx":1024,"heightPx":768}]
```

Audio uses durationMs. URLs are generated by the API. Validate individual attachment fields, permitted storage prefixes, file limits and ownership in the service; SQL enforces only the JSON container shape. Unsaved photo analysis is a draft and must not become a confirmed meal merely because analysis succeeds.

Nutrition tag_data:

```json
{"mealCategory":"lunch","items":[{"id":"item-uuid","name":"Rice","quantity":150,"unit":"g","caloriesKcal":195,"proteinG":null,"carbohydratesG":null,"fatG":null,"quantitySource":"user_entered","nutritionSource":"estimated"}]}
```

Calories refer to the recorded portion. Reference-based nutrition additionally retains provider, reference ID, reference amount and unit. Unknown macros remain null. Validate at least one named item, positive quantities, finite nonnegative calories and allowed sources before saving.

Exercise tag_data:

```json
{"activityName":"Walking","durationMinutes":30,"intensity":"moderate","estimatedCaloriesBurnedKcal":null,"calorieEstimationSource":null}
```

Validate positive duration and a named activity. Note tag_data may be `{}`. User corrections go into tag_data, AI proposals into ai_structured_data. User text stays in note; generated interpretation stays in ai_synopsis. audio_transcripts is an array keyed by attachment ID.

entry_date is the user-assigned reporting date; occurred_at is the actual instant. recorded_timezone preserves its interpretation. The service must define date assignment consistently and never silently regroup old entries when timezone changes. Daily calories derive from confirmed, nondeleted nutrition entities; exercise expenditure remains separate. There is no calorie allowance or remaining-calorie calculation without a confirmed target.

## Append-only health observations

Every record has a metric, value, unit, event time and source. Do not infer a new weight from the prior value. Extracted measurements require explicit input and user confirmation before being treated as accepted observations.

Corrections append a record pointing to supersedes_record_id. A deletion appends a void replacement. SQL rejects updates/deletes, branching replacements, corrections across owners/metrics/source entities, and wrong source ownership/revision. Each sourced metric can be emitted once per entity revision. Serialize correction chains and append the entity update and replacement observations in the same transaction.

Read active observations by excluding records that have a supersededBy record and excluding is_void records. For sourced observations, also require a nondeleted entity and source_revision = entity.revision. This prevents stale calculated observations contributing after edits or deletion, even before a replacement exists. Weight display chooses the latest active observation; calories remain derived from entity facts rather than summed from every log row.

## AI lifecycle

One current workflow per entity is embedded in its details, with attempt count, next-attempt time and lease expiry. Workers must claim pending work atomically, recover expired leases, enforce retry limits, and save outputs only when the entity's current revision equals ai_input_revision. Entity content edits automatically advance revision; AI output updates do not. SQL does not implement the worker or external provider calls. Use a row lock or atomic compare-and-update when applying AI output to avoid concurrent edits.

## Conversation contract

A thread selects the model for future requests. An assistant message stores actual_model_id, including fallback attribution. Secrets remain in backend configuration; credential_reference is only a configuration name and should be excluded from public DTOs.

Use one request_id for the user/assistant pair. Unique (thread_id, request_id, role) prevents duplicate retries; unique sequence numbers preserve ordering. A partial SQL unique index allows only one pending/processing assistant reply per thread. Replies cannot reference a message in a different thread. Create messages and allocate sequence numbers while holding the thread row lock.

Message metadata contains references, not just retrieval function names:

```json
{"retrieval":{"functionNames":["getNutritionHistory"],"entities":[{"entityId":"uuid","revision":2}],"healthRecordIds":["uuid"]}}
```

Validate retrieved IDs against thread ownership in the service. Track processing/completed/failed/cancelled status and preserve the existing request on retry. Cancellation, credential verification, guest chat gating and actual network processing are service responsibilities.

## Migration

The initial migration includes SQL checks, partial indexes and triggers that Prisma cannot express. Deploy with `pnpm prisma:deploy` after reviewing the target database. Do not replace this with db push, which does not install the custom SQL contract. Client generation and schema validation do not apply the migration.
